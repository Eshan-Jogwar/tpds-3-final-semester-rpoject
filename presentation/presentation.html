04 · TECHNICAL ARCHITECTURE

Full-Stack Architecture and Technology Stack

Decoupled 3-Tier Design with On-Disk SQLite Storage and Containerization
3-TIER SYSTEM
Figure 2: Full-stack system architecture illustrating decoupled tiers, RESTful communication, and Docker orchestration.
Tier 1: Presentation Layer CLIENT RUNTIME
  • Bootstrap 5.3 framework with custom responsive CSS tokens.
  • Modular ES6+ JavaScript (zero build step overhead, instant browser execution).
  • Chart.js 4 for dynamic resolution analytics and category distributions.
  • Interactive 2D SVG Campus Blueprint with real-time room severity styling.
Tier 2: Application Layer (REST API) NODE 20 LTS
  • Node.js 20 LTS runtime executing Express.js 5.1 with native async exception handling.
  • Structured controllers for `/api/v1/tickets`, `/facilities`, `/departments`, and `/analytics`.
  • Server-side request validation, input sanitization, and SLA countdown calculation.
Tier 3: Persistence Layer SQLITE WAL
  • SQLite 3.45 engine driven via high-performance better-sqlite3 driver.
  • Write-Ahead Logging (PRAGMA journal_mode = WAL) for non-blocking concurrent reads.
  • Foreign key constraints strictly enforced (PRAGMA foreign_keys = ON).
CONTAINERIZATION & ORCHESTRATION SPECIFICATION
Official node:20 LTS base image with pre-compiled glibc. Docker named volume (campuspulse-data) mounted to /app/data guarantees persistent database survival across restarts.

05 · DATA ENGINEERING & SCHEMA

Relational Schema and Normalization Strategy

Third Normal Form (3NF) Architecture with Materialized Analytical Views
3NF RELATIONAL MODEL
Figure 3: Relational 3NF database schema showing primary keys, foreign key relationships, and analytical views.
5 NORMALIZED RELATIONAL TABLES
• departments: (id [PK], name, code, contact_email, sla_hours)
• users: (id [PK], name, email, role, department_id [FK])
• facilities: (id [PK], name, building, floor, room_number, dept_id [FK])
• tickets: (id [PK], ticket_number, facility_id [FK], dept_id [FK], priority, status, sla_deadline, photo_url)
• ticket_audit_logs: (id [PK], ticket_id [FK], changed_by [FK], old_status, new_status, notes)
NORMALIZATION VERIFICATION (3NF COMPLIANCE)
1NF (Atomicity): All fields hold atomic single values; zero comma-separated tags or nested arrays.
2NF (Full Functional Dependency): No non-prime attribute depends on a partial candidate key.
3NF (Zero Transitive Dependency): Facility room and department SLA details reside in dedicated tables, preventing update anomalies in ticket records.
ANALYTICAL VIEWS (DATABASE-TIER COMPUTATION)
• vw_department_sla_metrics: Computes total, resolved, breached tickets, compliance %, and average resolution duration in hours.
• vw_campus_hotspots: Aggregates unresolved incidents by building and facility, computing priority-weighted incident scores.
HIGH-VELOCITY QUERY INDEXING STRATEGY
idx_tickets_status_priority · idx_tickets_facility · idx_tickets_dept · idx_audit_ticket

Engineering Decisions, Performance, and Verification

TESTED & VERIFIED
STORAGE CONCURRENCY
Zero-Server SQLite & WAL Mode

Write-Ahead Logging allows non-blocking concurrent analytics querying during live ticket submission. A 5000ms busy timeout completely eliminates lock collisions.

BUSINESS LOGIC INTEGRITY
Deterministic State Machine

Enforced transitions: open → in_progress → resolved → closed. Every state change writes immutable records to ticket_audit_logs.

DEPLOYMENT & REPRODUCIBILITY
Dockerized Container Pipeline

Isolated container build with persistent named storage volume (campuspulse-data). Single-command management orchestrated via root Makefile.
